**计划 ID**：`PHASE3-PERSONAL-MINIMUM-REBASELINE-20260729`
**日期**：2026-07-29
**状态**：✅ 已独立审查通过（P0=0、P1=0）且用户已于 2026-07-28 采用个人版最小闭环；仅计划与任务清单登记，未改变 Phase 3 既有 WBS，未修改业务代码或执行真实操作；后续从 P1 开始逐项制定实施计划
**适用场景**：一名学生、家庭个人、本机 Windows、本地数据、无公网入口、无多用户、无家长登录或网页面板。

---

## 1. 目标与不可伪称的事实

本计划的目标是把当前 Phase 3 的实施方式从“18 个剩余必做 WBS 项分别形成独立开发日”压缩为少量可连续交付的**个人版最小闭环切片**，只保留个人本机使用真正需要的安全、数据保护、隐私和可用性结果。

本计划**不**宣称：

- 旧 WBS 的 18 个未完成必做项已完成、已取消或不再需要；
- `Phase 3`、顶层 `T02`、真实 R1/R2、真实 backup/restore 或用户电脑验收已完成；
- production trust anchor、release/install identity 或真实审批记录已配置；
- 当前合成测试是实际机器、真实秘密、真实 ACL 或真实备份/恢复证据。

在用户明确批准重定标决定前，`docs/04` 的正式计数仍为：25 个必做项、已完成 7 个、剩余 18 个。个人版最小闭环是一个**可安全使用的发布里程碑**，不是对旧 Phase 3 完成定义的静默替换。

1. 当前高权重恢复计划是 `.plans/phase3-reopen-high-weight-20260728-plan.md`，列出 11 项候选工作，但其 Wave 拆分仍偏向逐项治理。
2. 共同 trusted-approval/no-follow 接口、trust-anchor 合成实现、独立源码复审和主线复验均已进入 `origin/master`；production 仍固定 fail-closed，未接入 R1/R2。
3. 现有 trust-anchor 计划曾写“待主线集成”，已与事实不符；本计划只同步其状态为“已进入 `origin/master`”，不改变其 production fail-closed 结论。

## 3. 个人版最小闭环的组织方式：6 个交付切片

**当前范围门禁**：本计划不改变 `PHASE3-REOPEN-HIGH-WEIGHT-20260728` 的当前实施授权。当前可进入后续实施计划的仅为原已批准的 11 项：T02-R1、T02-R2、T04-1～T04-3、T02-R3、T05-1～T05-3、T02-R4、T02-R6。T01-1/2、T05-4、T03-1～T03-3、T02-R5 仅作为旧 WBS 的未来候选和计数事实展示，**不属于本计划的当前排程或后续实施计划范围**；如需纳入，必须另行制定范围扩展计划、独立审查并取得用户明确批准。

### P0：个人本机边界确认（纯文档，未来候选）

**旧 WBS 映射**：T01-1、T01-2；不进入本轮实施顺序。

- 继续保持“学生唯一操作者、家长只收既有异步脱敏报告、无公网入口、无家长登录/网页面板”这一既有边界事实。
- 不创建新产品形态、不改 PRD 业务需求、不引入账号、远程访问或家长面板。
- 如未来需要将这两个既有 WBS 验收点纳入，可共享一份简短决策记录和一次审查；在独立范围扩展批准前，不得制定或实施其计划。

### P1：同一窗口的两项只读安全证据

**合并映射**：T02-R1、T02-R2；两项证据、两项完成判定不得混淆。

- R1 只扫描 Git 已跟踪清单和用户单独批准的一个候选部署包根；绝不读取、枚举或扫描未跟踪目录或整个工作区。
- R1 只输出规则 ID、计数、脱敏 artifact ID、构建提交短哈希、包 SHA-256 短指纹、批准时间窗口和固定错误码；不得输出秘密值、环境变量、敏感相对文件名、原始命令或原始扫描输出。
- R2 只读 `config/data/logs/backups/tmp/models` 六类逻辑目录；拒绝 UNC、映射盘、非固定本地卷、reparse、未知主体、deny ACE、继承异常和有效访问未知。
- R2 不得 `Set-Acl`、写探针、创建文件、调用 backup/restore、触发服务或计划任务；只输出固定脱敏类别和是否建议未来另批最小 ACL 修复。
- 两项真实操作可以安排在同一**用户明确批准**的机器/制品/时间窗口中，以减少重复准备；每项仍需各自的计划、测试、独立审查和签收条目。

### P2：最小数据保护闭环

**合并映射**：T04-1、T04-2、T04-3、T02-R3。

- 用同一个最小实现计划完成受控备份、完整性检查和可恢复性设计；不建设企业灾备、远程复制或长期运维平台。
- T04-3 的任何真实恢复写入仍保持独立 pre-write / post-restore Gate；不能因与 T04-1/2/R3 同属 P2 而被自动批准。
- R3 只复核 T04 的安全边界与证据，不实现第二套备份/恢复功能。

### P3：最小日志隐私与容量保护

**合并映射**：T05-1、T05-2、T05-3；T05-4 继续排除，不进入本轮实施顺序。

- 一次实现一个小型本地日志契约：允许字段、统一事件/等级、脱敏、单文件与总量上限。
- 到达容量时必须可见且安全地停止新增日志；不得以“个人使用”或“容量控制”为由删除历史日志、建立保留期或安全清理机制。
- 不建设集中日志平台、远程上传、复杂分析、企业审计检索或多租户规则；不保留秘密或学生原文。

### P4：孩子可理解的失败反馈

**合并映射**：T02-R4。

- 只覆盖当前实际使用的 S1/S2/S4/S5/S7 主路径和已经存在的错误响应边界；不提前为未启用 Worker 或未建设的功能扩展。
- 统一给出脱敏中文提示、可重试建议和固定错误分类；不展示内部堆栈、路径、Provider 原始输出或配置细节。

### P5：一次性个人机验收与风险记录

**合并映射**：T02-R6；T03-1～T03-3、T02-R5 继续排除，不进入本轮实施顺序。

- 将 P1/P2/P3/P4 的已批准范围证据、剩余风险、浏览器草稿/文档漂移和责任边界放入一个简短风险记录；不建立企业风险治理体系。
- T02-R6 只能在已批准范围内的 R1/R2/R3/R4 证据闭合后签收；即使 T02 签收，也不得宣称旧 Phase 3 的 T01/T03/T04/T05 全部完成，除非对应 WBS 也有验收事实。
- 启动、常用核心流程、主要页面、内存/CPU/残留进程、磁盘占用和重复运行的个人机验收，以及 T03-1～T03-3、T02-R5，均是未来候选；如需纳入，必须先单独范围扩展、独立审查和用户批准。

## 4. production trust anchor 的个人版决策选项

当前主线已有 fail-closed 的共同模块；它没有 production key，也没有 release/install identity。个人版不应私自把测试 key、环境变量、普通配置或目录 ACL 当作 production trust anchor。

本计划推荐用户在独立审查后选择以下两种之一：

1. **个人版推荐：不接入该模块**。保留它为未接入、固定 fail-closed 的共同库；R1/R2 以每次真实运行前用户在本任务中的精确批准为授权来源，不自动操作、不后台运行、不持久化真实审批记录。此选择降低企业级可审计性，但适合单用户本机、每次人工确认的范围。
2. **严格方案：另行配置真实 trust anchor 与 release identity**。仅当需要可转交的签收、多人管理、外部部署或自动化操作时才采用；必须另计划、独立审查、由受控渠道提供真实三元组并获用户单独批准。

无论选择哪一种，P1 的“无秘密输出、R1 受控输入、R2 严格只读、fail-closed 分类”均不降低。
