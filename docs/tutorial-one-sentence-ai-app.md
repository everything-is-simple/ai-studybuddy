# 零基础实操教程：一句话让 AI 自动搭建应用

> **适合谁**：完全不懂编程，但想自己做一个小工具的人。
> **你需要什么**：一个 AI 对话工具（Claude / GPT / 通义 / DeepSeek 均可），加一个记事本。
> **读完你会得到**：一套从零到一让 AI 帮你把想法变成可用产品的完整方法。

<a id="核心思路"></a>
## 核心思路：不是让 AI 写代码，是让 AI 当你的团队

大多数人用 AI 写代码的方式是这样的：

> "帮我写一个记账 App。"

AI 吐出一坨代码，你复制粘贴，跑不通，再问一句，如此循环。**你把 AI 当成了代码片段生成器。**

正确的做法是——**把 AI 当成一个完整的技术团队**。让它依次扮演：

| 角色 | 负责什么 |
|------|---------|
| 高级开发 | 跟你聊需求，追问细节 |
| 产品经理 | 把需求整理成文档 |
| 前端架构师 | 设计界面和交互规范 |
| 后端架构师 | 设计数据库和接口规范 |
| 测试工程师 | 写测试计划 |
| 项目经理 | 拆解任务清单 |
| 开发工程师 | 逐个执行任务写代码 |

**你只需要做一件事：审核和打勾。**

这就像盖房子——你不会自己搬砖，但你需要先画好图纸，再请工人按图纸施工。这里的"图纸"就是文档，"工人"就是 AI。

<a id="第一阶段"></a>
## 第一阶段：跟 AI 聊天，把想法"逼"清楚（30-60分钟）

### 你只需要说一句话

打开 AI 对话框，粘贴这段话作为开场白：

```
你现在是一位拥有 10 年经验的高级全栈开发工程师。我有一个工具的想法想和你讨论。
请你不要急于给出方案，而是像一个负责任的技术合伙人一样，针对我的描述，
不断追问细节、挑战我的假设、帮我理清需求边界。
我们的目标是：在对话结束时，所有的功能需求、交互细节、技术约束都已经清晰无歧义。
```

然后说出你的想法，哪怕只有一句话：

```
我想做一个帮大学生记录课堂笔记、AI自动整理、还能让家长看到学习状态的工具。
```

### AI 会追问你 20-40 个问题

比如：
- 学生用什么设备？手机还是电脑？
- 录音要不要自动转文字？用什么方案？
- 家长能看到什么？能看到分数吗？能看到错题吗？
- 离线的时候怎么办？

**关键原则：老老实实回答每一个问题。** 你在这里偷的每一个懒，都会变成后面开发时的混乱。

当你回答到 AI 说"需求已经比较清晰了"的时候，这个阶段就完成了。

<a id="第二阶段"></a>
## 第二阶段：把聊天变成一份"图纸"（PRD）

### 什么是 PRD？

PRD（产品需求文档）就是你跟 AI 聊了半小时之后，把所有结论写成一份正式的文档。**它是后面所有工作的"唯一真相来源"。**

为什么不能跳过这步？因为：
- AI 的对话记忆有限，聊久了早期内容会被"遗忘"
- 文档可以跨会话使用——新对话里喂入文档，AI 立刻恢复全部上下文
- 你能在文档里发现聊天时没注意到的矛盾和遗漏

### 让 AI 自己整理 PRD

在聊天快结束时，直接说：

```
请根据我们刚才的所有对话，整理一份完整的产品需求文档（PRD.md）。
要求包含：项目概述、目标用户、核心功能列表（按优先级排列）、
详细功能描述（含交互细节和边界情况）、非功能性需求、技术约束、
暂不实现的功能（明确标注不做的事）。
```

AI 会输出一份结构清晰的文档，你保存到文件 `PRD.md`。

### 你一定要做的事

**通读一遍 PRD，用你自己的话检查每个功能描述是否与你的预期一致。** 发现不对的地方，直接改或者再跟 AI 讨论一轮。

<a id="第三阶段"></a>
## 第三阶段：让 AI 一人分饰六角，生成 9 份文档

这是整个流程中**信息密度最高**的一步。你要让 AI 戴上不同的"帽子"，从不同角度审视同一份 PRD，产出多份技术文档。

### 为什么需要这么多文档？

打个比方：PRD 是"房子要长什么样"，但这些文档是"怎么盖"——结构图、水电图、装修图……每张图解决一个问题。**AI 执行代码时，这些文档就是它的施工图纸。**

### 9 份文档生成顺序

**每份文档开一轮新对话**，把 PRD.md 作为上下文带进去。按这个顺序来：

| 序号 | 文档名 | AI 扮演角色 | 一句话作用 |
|------|--------|------------|-----------|
| 1 | `dev-rules.md` | 技术主管 | 给 AI 定规矩——代码风格、禁止事项、修改铁律 |
| 2 | `frontend-guidelines.md` | 前端架构师 | 界面长什么样——配色、组件规范、交互原则 |
| 3 | `backend-guidelines.md` | 后端架构师 | 后台怎么搭——数据库、接口、安全方案 |
| 4 | `architecture.md` | 系统架构师 | 整体蓝图——模块划分、数据流、技术选型 |
| 5 | `test-plan.md` | 测试工程师 | 怎么验收——测试用例、覆盖范围、质量标准 |
| 6 | `todo-list.md` | 项目经理 | 施工排期——拆成一个个可执行的小任务 |
| 7 | `lessons.md` | （空文档） | 踩坑记录，开发过程中积累 |
| 8 | `buglist.md` | （空文档） | Bug 追踪，开发过程中积累 |
| 9 | `PRD.md` | （已有） | 第一阶段产出 |

### 第 1 份最重要：dev-rules.md

这份文档是给 AI 的"紧箍咒"。没有它，AI 改 Bug 时可能顺手把你的代码重构了；加功能时可能偷偷改了之前的逻辑。有了它，AI 每次干活前都要戴上这个"紧箍咒"。

生成 Prompt：

```
你现在是技术主管。请阅读 PRD.md，输出一份 AI 开发规范文档（dev-rules.md）。
核心内容：代码风格规范、AI 修改代码时的铁律（只改必要部分、不删已有注释、
完成后列出改动点）、绝对禁止事项（不用 any、不硬编码密钥）、
Git 提交规范、文件组织结构。
这份文档会在每次开发对话中作为上下文提供给 AI。
```

### 生成 todo-list.md 的 Prompt（最关键）

```
你现在是项目经理。请阅读 PRD.md、architecture.md、frontend-guidelines.md、
backend-guidelines.md、test-plan.md、dev-rules.md。
请将整个项目拆解为 todo-list.md：
1. 按开发顺序排列（考虑依赖关系）
2. 每个任务粒度控制在单次对话可完成
3. 每个任务注明：描述、输入文件、输出文件、验收标准
4. AI 容易出错的环节用 ⚠️ 标注
5. 使用 checkbox 格式
```

### 完成后的文件夹结构

```
my-project/
├── docs/
│   ├── PRD.md                  # 产品需求（已有）
│   ├── architecture.md         # 架构蓝图
│   ├── frontend-guidelines.md  # 前端规范
│   ├── backend-guidelines.md   # 后端规范
│   ├── test-plan.md            # 测试计划
│   ├── dev-rules.md            # AI 紧箍咒
│   ├── todo-list.md            # 任务清单
│   ├── lessons.md              # 踩坑记录（空）
│   └── buglist.md              # Bug 追踪（空）
└── src/                        # 代码目录（即将填充）
```

**注意：到这里你还没写一行代码，但你已经有了一个比大多数个人项目都完善的文档体系。** 这就是后面"AI 自动施工"的基础。

<a id="第四阶段"></a>
## 第四阶段：AI 干活，你验收

终于到写代码了。但你的角色不是"写代码的人"，而是**验收者**。

### 每次执行任务的标准流程

```
1. 打开新对话
2. 喂入上下文（dev-rules.md + 当前任务描述 + 相关代码）
3. AI 生成代码
4. 你对照验收标准检查
5. 通过 → 打勾，下一个任务
   不通过 → 记录到 buglist.md，让 AI 修复
```

### 每次对话的开场白模板

```
我正在开发 [项目名]。以下是项目核心文档：
- dev-rules.md（开发规范）：[粘贴]
- 当前任务来自 todo-list.md 的任务 X.X：[粘贴任务描述]
- 相关架构设计：[粘贴 architecture.md 中相关章节]
- 当前已有代码：[粘贴相关文件]

请严格按照 dev-rules.md 执行。完成后列出所有修改点。
```

### 踩坑了怎么办？

**分两种情况处理：**

| 情况 | 记录到哪 | 例子 |
|------|---------|------|
| 代码逻辑错了 | `buglist.md` | 登录功能密码校验写反了 |
| AI 行为模式有问题 | `lessons.md` | AI 改功能 A 时顺手把 B 也改了 |

如果是 AI 行为问题，从 `lessons.md` 中提炼出一条通用规则，反向补充到 `dev-rules.md`。

**这是一个自我进化的正循环：踩坑 → 记录 → 提炼规则 → 补充到紧箍咒 → AI 不再犯同样的错。**

<a id="第五阶段"></a>
## 第五阶段：什么时候算做完？

验收通常要经历 3-5 轮循环：

| 轮次 | 状态 |
|------|------|
| 第 1-2 轮 | Bug 高发期，主要功能逻辑问题 |
| 第 2-3 轮 | 优化需求爆发，"这里加个提示更好" |
| 第 3-4 轮 | 收敛期，Bug 明显减少 |
| 第 4-5 轮 | 收尾期，只剩零星小问题 |

**完成标准：**
- 核心功能全部正常，连续 2 轮无 Bug
- 没有数据丢失或安全风险
- 你自己愿意每天用它

满足以上三条，v1.0 就算做完了。剩下的优化点放进 `todo-list.md` 的 "Future" 章节，留给下个版本。

## 实操 Prompt 速查表

把下面这些 Prompt 复制保存，按顺序用就行：

### 第一步：需求对话

```
你现在是一位拥有 10 年经验的高级全栈开发工程师。我有一个工具的想法想和你讨论。
请你不要急于给出方案，而是不断追问细节、挑战我的假设、帮我理清需求边界。
```

### 第二步：生成 PRD

```
请根据我们的对话，整理一份完整的 PRD.md。包含：项目概述、目标用户、
核心功能列表（P0/P1/P2）、详细功能描述、非功能性需求、技术约束、暂不实现的功能。
```

### 第三步：依次生成 9 份文档

```
# dev-rules.md
你是技术主管，阅读 PRD.md，输出 AI 开发规范：代码风格、修改铁律、禁止事项、Git 规范。

# frontend-guidelines.md
你是前端架构师，阅读 PRD.md，输出前端设计原则：UI 规范、组件原则、状态管理、响应式方案。

# backend-guidelines.md
你是后端架构师，阅读 PRD.md，输出后端架构原则：技术栈、API 规范、数据库设计、安全方案。

# architecture.md
你是系统架构师，基于 PRD + frontend/backend guidelines，输出整体架构：模块划分、数据流、技术决策。

# test-plan.md
你是 QA 工程师，阅读所有文档，输出测试计划：测试策略、核心用例、验收标准。

# todo-list.md
你是项目经理，阅读所有文档，拆解任务清单：按顺序排列、粒度合适、标注验收标准和 ⚠️ 风险点。
```

### 第四步：执行每个任务

```
我正在开发 [项目名]。
dev-rules.md：[粘贴]
当前任务：[粘贴 todo-list.md 中的任务描述]
相关代码：[粘贴]
请严格按规范执行，完成后列出所有修改点。
```

---

## 最后说三句话

1. **文档先行，杠杆极高**——你不是给自己写文档，是给 AI 写工作手册。文档越精确，AI 表现越好。

2. **小步快跑，不要贪多**——每次只做一个任务，做完就验收，验收通过再做下一个。

3. **踩坑是好事**——每次踩坑都记录并补充到 dev-rules.md，AI 会越用越聪明，这是一个自我进化的正循环。

**这不是关于 AI 有多强大的故事，是关于你如何组织和驾驭 AI 的能力的故事。**
